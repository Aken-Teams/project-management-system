方案 A

嚴格層級綁定

父層日期 = 子層的最早開始 ～ 最晚結束，系統自動算、自動貼齊。
✓子任務全部起訖 = 任務起訖（完全涵蓋）
✓任務全部起訖 = 里程碑起訖（完全涵蓋）
✓改子任務 → 父層日期自動跟著變，永遠對齊
✓報表 / 甘特圖一定一致，不會有「父比子短」的矛盾
✗父層日期不能單獨手動調（它是算出來的）
✗使用者改了父層格子，下次重算又被蓋回 → 覺得「亂跳」
適合：重視資料一致、報表正確、稽核可信。代價是彈性低，父層只能透過改子層來動。
方案 B

彈性日期 + 不一致警示

子任務改 → 任務跟著建議；但任務也可往內縮，子任務不硬性跟隨，僅以 ⚠ 提示。
◆任務日期可獨立手動設定（彈性卡控）
◆允許任務範圍小於子任務（父 < 子），不強制涵蓋
◆不一致時跳 ⚠ 告知，由人判斷是否合理
✓任務可代表「審查點 / 關鍵節點」，不必把所有細項包進去
✗父子日期可能不一致，需各自維護、人工確認
✗跨里程碑連動：改了這裡的任務，可能又牽動到別處的父層（見下方③）
適合：客戶要高度彈性、任務當審查點用。代價是父層不再等於子層總和，甘特可能出現父短子長，需人工確認合理性。

③ 隱藏陷阱（A / B 都會中）：兄弟重疊，讓「天數對不起來、改了沒反應」

系統允許同層項目重疊（例：子任務 A 1/15～1/20、子任務 B 1/18～1/30）。父層 = 子層的最早開始～最晚結束（跨度），不是工期相加。這會從兩個方向製造誤解，自己拉拉看：

④ 方案 B 要先想清楚的隱憂：跨里程碑連動

你提到的困擾就在這裡：方案 B 允許「子任務 → 任務」連動。當你在里程碑二裡調好了某個任務， 它的子任務若同時被別的規則牽動，又會回頭去動里程碑一那邊已經喬好的任務 —— 變成「這區改好、那區又跑掉」。 本質是：彈性一旦開放到「每一層都能互相牽動」，連動鏈就會跨越里程碑，難以預期。
收斂方式：把「彈性」限制在葉節點（最底層子任務），連動只「由下往上」單向傳遞、不橫向跨里程碑。 父層（里程碑、含子任務的任務）一律是「算出來的結果」而非「可被牽動的輸入」，就不會出現 A 區改好、B 區跑掉的情況。

⑤ 不論選 A 或 B，都要先決定：延後與提前該不該對稱？

這是讓使用者覺得「系統不照我改」的隱藏主因 —— 延後往下順延很合理，提前卻不一定該把下游一起往前拉。

⑥ 給客戶的關鍵決策問題

用三個問題，就能決定要走哪個方案

Q1．你有沒有一種里程碑 / 任務，是你「刻意」讓它的截止日比裡面最晚的工作還早結束？
沒有 → 你要的其實是 方案 A（彈性放在子任務即可，父層自動算）。
有 → 你需要 方案 B，並接受父子可能不一致、需人工確認。
Q2．「彈性」你要開到哪一層？
只要能決定每件事「做幾天、哪天做」 → 彈性放在葉節點就夠（A 即可）。
連「父層日期要獨立於子層」都要 → 才需要 B 的橫向彈性（但要承擔③的連動風險）。
Q3．當一個里程碑「提前」完成，後面的里程碑要「跟著提前」還是「維持原承諾日」？
維持原承諾日（多數情況）→ 提前不該無腦 cascade 到下游。
跟著壓縮 → 才讓提前往下傳遞。
