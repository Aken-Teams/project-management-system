# 協作與需求變更管理（給開發端的專業建議）

> **用途**：處理「user 需求反覆、結案又提新需求、把未確認需求說成 bug、驗收落差」造成的內部紛爭與溝通 gap。
> 這不是程式問題，是**流程與治理問題**。程式再乾淨，缺了這套機制，紛爭不會停。
> **建立**：2026-07-07

---

## 一、先把問題命名清楚（否則會一直吵錯地方）

你現在的痛苦，本質是三個「真空」造成的，情緒只是填進真空裡的東西：

1. **「完成 / 結案」沒有定義** → 所以每次結案都能被重新打開。
2. **「bug vs 需求變更」沒有客觀判準** → 所以誰情緒大誰說了算。
3. **「驗收」沒有紀錄** → 所以「你當初沒測」和「我交的時候是好的」變成各說各話。

> 核心心法：**你無法控制 user 的情緒，但你可以抽掉情緒賴以生長的『模糊』。** 情緒在事實真空裡才會失控。每次你把「我覺得那時是好的」換成「這是簽收單 + 那天通過的測試」，衝突就少一分。目標不是讓 user 變講理，是讓**事實不可爭辯**。

---

## 二、Bug vs 需求變更：用「文件」畫線，不是用「誰比較兇」畫線

**唯一客觀的判準：**
> **Bug** = 行為偏離「一份雙方已書面確認的規格」。
> **需求變更** = 那份「已確認的規格」本身要改。

**推論：如果沒有書面確認的規格，那所有東西都可以被說成 bug** —— 這正是你被綁死的原因。解法不是跟 user 辯，是**讓每個迭代都有一份簽核過的規格**，讓那條線由文件劃，不是由當下誰比較生氣劃。

### 實務分類表（每張單子進來先貼標籤）
| 類型 | 定義 | 處理 | 收費/計時 |
|------|------|------|-----------|
| **A. 真 Bug** | 偏離已確認規格 | 優先修，免費 | 不另計 |
| **B. 規格漏洞** | 規格沒寫到、雙方都沒想到的細節 | 補規格 → 當小型變更 | 視情況 |
| **C. 需求變更** | 已確認的東西要改方向 | 走變更流程、重新估、排期 | 另計 |
| **D. 假 Bug 真變更** | user 把「我改想法了」包裝成「這是 bug」 | **溫和拆解**：指出哪部分是真 bug（照修）、哪部分是方向改變（走變更） | 拆開計 |

> D 類是你最常遇到的。關鍵不是拒絕，是**當場拆給他看**。例：相依/連動案 → 「server 無視手動日期是真 bug，我這版修掉；但『瀑布改成可重疊』是您需求方向從 A 變 B，這是變更，我們排下一版。」把 1 個 bug 和 1 個變更分開，情緒就降溫，因為他發現你不是在推、你是在分。

## 三、驗收機制：這是對付「你當初沒測」的唯一武器

你描述的最痛場景：**改了 10 個，user 只測 3 個，5 版後才說當初那 7 個有問題。** 防禦要三層：

1. **每次交付附「交付清單 + 驗收單」**：列出這版改了哪 N 項；user 逐項勾「已測/通過」或「未測」。
2. **建立規則（事前講好，白紙黑字）**：
   > 「**已驗收 = 已測且確認**。未勾選項目屬『已交付未驗收』，事後才發現問題視為**新單**，不算本次交付的回歸。」
   這不是刁難，是**讓收斂成為可能**的唯一方式。沒有這條，專案永遠無法結束。
3. **未回覆即視同驗收**：交付後設一個回覆期限（如 5 個工作天），逾期未提異議即自動驗收。避免 user 無限期不測又無限期保留追訴權。

---

## 四、版本凍結與「結案」的定義

「每次結案都生出新需求」是因為**結案沒有定義**。建議：

- **每個版本有明確範圍 + 凍結線**。凍結後進來的，一律進 backlog、排**下一版**、**重新估**。
- **結案 = 本版範圍內項目全數驗收**。之後的需求是「新階段」，不是「還沒結束的舊案」。
- 這條要**在合約/報價層級講清楚**，不然工程端再自律也擋不住。

---

## 五、自動化測試 = 你最強的「證據」（重新定位它的價值）

你之前提到要「自動測試」。**專業建議：現在就投資自動化回歸測試，但理由不只是程式品質，是『契約證據』。**

- 當 user 說「當初那 7 個是壞的」，你能拿出 **「commit X、某月某日，這 7 項的測試全綠」** → 把「他說/你說」變成**時間戳記 + 通過紀錄**。
- 這是把 §三 的驗收落差從「人的記憶」升級成「機器的紀錄」。爭議成本直接歸零。
- **投資順序**：先為第五章的 12 個 bug 寫回歸案例（防止修好又壞），再為核心流程（建案、時間軸編輯、延期審核、進度計算）寫 API 整合測試，最後才是 Playwright UI 冒煙。
- 每次交付**跑一次、附報告**。測試報告就是驗收單的客觀背書。

> 現況：專案無任何測試框架。這是目前最值得補的一塊，且它同時服務「品質」與「防紛爭」兩個目的。

## 六、溝通節奏與文件化（把知識變成可共享的紀錄）

| 時機 | 產出 | 目的 |
|------|------|------|
| 需求進來 | **變更單**（描述、分類 A/B/C/D、估時、影響範圍） | 事前對齊，避免做完才發現理解不同 |
| 開工前 | user **書面確認**變更單 | 劃出「已確認規格」那條線 |
| 交付時 | **交付清單 + 測試報告 + 驗收單** | 事後可追溯 |
| 驗收後 | 更新 `system-audit.md` 第七章變更紀錄 | 累積可查歷史 |

- `docs/system-audit.md`（系統現況 + bug 清單 + 變更紀錄）本身就是**對付「這是不是 bug」爭議的內部證據庫**。ADR-01（相依/日期）就是範例：下次 user 再說連動是 bug，翻出來即可。
- **每次改動 = 一個 git tag + changelog**。「當初那 7 個」→ 對應到某個 tagged 版本 + 當時的驗收單。

## 七、給你的立場建議（心態層面）

1. **你「真 bug 照修、需求反覆不算 bug」的立場是對的** —— 問題不在立場，在缺少讓立場站得住的文件。先補文件，立場自然硬。
2. **不要試圖預測 user 的情緒**，那會把你綁死。改成**降低模糊**：每個模糊點都補一份紀錄，情緒就沒有燃料。
3. **拆解、不對抗**。D 類（假 bug 真變更）當場拆成「這塊我修、這塊算變更」，比整包拒絕有效十倍——因為 user 感受到的是「你在幫我分清楚」，不是「你在推責任」。
4. **對內（團隊）先統一口徑**：內部先用 A/B/C/D 分類每張單，吵架會少很多，因為大家在吵「這是哪類」而不是「這該不該做」。
5. **把重構當機會不是包袱**：像相依/日期這種「越改越繁瑣」的地基，趁一次需求變更把它換成絕對日期模型（ADR-01），未來的變更成本會大幅下降——這也是你能對 user 提的正當「技術債清償」議題。

---

## 八、可以馬上開始的三件小事（低成本、高槓桿）
1. 下一張需求單進來時，**先貼 A/B/C/D 標籤**再動工，並讓 user 書面確認。
2. 下一次交付時，**附一張逐項驗收單**，講好「未勾選=未驗收，事後算新單」。
3. 開始為**第五章的 bug** 寫第一個自動化回歸測試——不用一次到位，一個一個累積。
