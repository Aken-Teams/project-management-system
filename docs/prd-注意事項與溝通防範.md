# PRD 注意事項與溝通防範（自我提醒）

> 用途：保護自己、避免誤會；萬一誤會發生，知道怎麼防範、怎麼說、用什麼態度。
> 心法：**紀錄不是拿來堵嘴，是把「各自的記憶」換成「同一份大家看得到的事實」。用對心態會降溫，用錯會激化。**
> 建立：2026-07

---

## 一、事前：讓 PRD 站得住的 4 個重點

1. **每條 PRD 配一句「驗收標準」**
   只寫功能名稱（如「可編輯里程碑日期」）會被鑽。補一句「怎樣算做到」→ 含不含連動、含不含重疊，寫清楚。**有驗收標準的那條線，對方鑽不進去。**

2. **先把現行版本凍成乾淨基準線**
   把「已交付✅」和「規劃中🔸」切乾淨，明確標「到 vX 為止＝這一階段範圍」。**基準線本身要乾淨，錨才錨得住。**

3. **PRD 沒有就不做，新需求走重新開案**
   但這只對付「新範圍」，不對付「真 bug」（見第二節）。

4. **設計變更一定要對方簽核/回覆背書**
   只有自己單方面寫的變更紀錄，事後仍會被說「我沒同意過」。**沒有對方確認的紀錄，等於沒有紀錄。**

---

## 二、判斷：這是 bug 還是新需求？

**一句話判準：**
> **偏離 PRD 的行為 = bug** → 我照修、免費、快修。
> **PRD 本身要改 = 新需求** → 走設計變更、重新開案。

**⚠️ 唯一會反噬自己的地方：別讓「不在 PRD」誤傷真 bug。**
如果把真正的缺陷也用「這不在 PRD」擋掉 → 等於送對方一個站得住的委屈（「連 bug 都用 PRD 當藉口不修」）。這條線守住，才佔理。

**遇到「假 bug 真變更」時 → 當場拆，不整包拒絕：**
> 「這裡面有兩塊：A 這塊是我們沒做到 PRD 寫的，算我們的，我這版修掉；B 這塊是您希望的方向和 PRD 原本不同，屬設計變更，我們排下一階段。」
拆解比對抗有效——對方感受到「你在幫我分清楚」，不是「你在推責任」。

---

## 三、誤會發生時：說明的「內容」與「態度」

**內容（拿事實，不拿情緒）：**
- 翻出 PRD 對應條目 + 當時的簽核/確認紀錄 + 交付清單/測試報告。
- 用「我們一起對一下當初 PRD 寫的」開場，不是「你看你當初就同意了」。
- 把爭點縮小到具體某條 PRD，不要擴大成「你老是反覆」。

**態度（降溫，不激化）：**
- **對齊，不對抗**：目標是「找出我們認知的差異在哪」，不是「證明你錯」。
- **先認同能認同的**：真有做不到的地方，先大方認：「這塊確實是我們的，我修。」先讓對方感覺你不是全推，後面的線才劃得住。
- **對事不對人**：只談 PRD 條目與紀錄，不評論對方的反覆或情緒。
- **不當場加價/當場翻臉**：金額、範圍爭議留到有紀錄可對照時再談，避免情緒下對決。

**一句可反覆使用的定調：**
> 「不是要爭誰對，是想確認我們對這條的理解是不是一致——PRD 這邊是這樣寫的，我們照這個做；如果您要的和這個不同，那我們就把它當一個變更好好排進去。」

---

## 四、心態提醒（給自己）

1. **紀錄能鎖住的是「你的下限」**——讓對方的情緒和反覆不再能任意改寫歷史。它做不到讓對方變講理，別要求更多，不然會失望。
2. **保護自己 ≠ 對抗對方**。同一份紀錄，用來對齊會降溫，用來堵嘴會反彈。時時檢查自己是哪一種。
3. **修改也要雙向遵守 PRD**：自己要改設計（如編輯/日期模型），也得先進 PRD 走變更，別偷改——否則反被說「你們自己亂動」。
4. **對內先於對外**：老闆已定「以 PRD 為主」，善用這個靠山；遇爭議先內部對齊口徑，再面對客戶。
