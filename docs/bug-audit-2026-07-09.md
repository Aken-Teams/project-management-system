### #5 延期 cascade 實質是 no-op ⚠️🔀

## 🟠 P1 — 正確性 / 顯示不一致

### #6 三套「今天」定義，逾期/狀態差一天 🔧
- **位置**：`lib/date-utils.ts:9` `todayUtc()`（UTC 午夜，server 用）vs `gantt-chart.tsx:154` `new Date()`（本地含時刻，今天線 + 逾期判定 `today > new Date(task.endDate)` 行 278）vs `milestone-task-view.tsx:271,277` `new Date()`（本地）
- **現象**：前端 `today`（帶時刻）> `endDate`（UTC 午夜）→ 只要到截止日**當天**前端就判逾期；server 用 `<=` 含當天。本地清晨（UTC 前一日）也會差一天。
- **後果**：逾期紅字/橘條可能比 server 狀態早一天出現，畫面與 DB / 里程碑徽章互相矛盾。
- **建議**：前端一律改用 `lib/date-utils` 的 `todayUtc()`/`todayUtcStr()`，逾期判定用日級（去時刻）比較。

### #7 `reportOnly` 型別 / 註解 / schema 三方矛盾 🔀
- **位置**：`lib/sync-milestone-status.ts:203-214`（型別有 `reportOnly?` 但函式沒讀、呼叫端 `select` 也沒撈）、`prisma/schema.prisma:338`（註解：「進更新紀錄但**不驅動進度**」）
- **現象**：schema 說 reportOnly 不驅動進度，但近期改成 A 的報告（一律 `reportOnly:true`）會用其 logDate 推算進度、甚至把 effStart 前拉。三方各說各話。
- **需你確認的需求**：**A 純敘述性的報告，到底該不該驅動時間進度？** 這是「需求反覆」高風險點，先確認語意再決定要不要改。
- **建議**：確認後，若不該驅動 → 呼叫端 select reportOnly 並在進度計算過濾；若該驅動 → 刪掉誤導的 schema 註解與死參數。

### #8 publish 不寫 `weekOf`，R 紀錄落到錯的週 🔀
- **位置**：`components/weekly-activity-summary.tsx:134`（`log.weekOf || getWeekMonday(log.logDate)`）、`tasks/[taskId]/route.ts:155-157`（publish 時不寫 weekOf）
- **現象**：若 #1 修好讓 R 紀錄被 publish，但 publish 只設 `publishedAt`，不設 `weekOf` → 退回用 `logDate` 落週。R 常補填上週（logDate 是上週），紀錄落上週，和 A 的彙整（依 weekOf 分組）分屬不同週卡片。
- **建議**：publish 時一併寫入該次彙整的 `weekOf`。

### #9 逾期未按完成的任務，進度掉回 0 🔧
- **位置**：`lib/sync-milestone-status.ts:251-253`
- **現象**：自動計算只保留 `d <= endDate` 的 log；若任務逾期、只在逾期後回報、又還沒按「完成」（無 completedAt），則所有 log 被濾掉 → `logsUpToEnd` 為空 → progress 歸 **0**，即使先前已有 60%。
- **後果**：進行中、跨截止日的任務，進度突然歸零倒退。
- **建議**：`allLogs` 非空但 `logsUpToEnd` 為空（全逾期）時，不歸 0；保留 99% 或維持現有 progress。

### #10 父任務「有 % 卻沒實際條」 🔧
- **位置**：`gantt-chart.tsx:739`（`parentHasActivity = earliestLogDateMap.has(task.id)`）、`898`（實際條繪製條件）、`736`（`aggregatedProgress = task.progress`）
- **現象**：父任務 % 可能來自子層 rollup（`tasks/[taskId]/route.ts:187-217`）而非零；但實際條只看「父自己有沒有 log」。→ 父任務顯示有 %，卻不畫實際條。
- **建議**：父任務實際條的來源與 % 同源（% 來自子層時，實際條也用子層最早 log）。

### #11 延期紅段依賴會被清掉的 original 欄位 🔧
- **位置**：`gantt-chart.tsx:582-601, 650-662`（用 `originalStartDate/EndDate` 判斷延期段）；清除來源 `app/api/projects/[id]/route.ts:331-349`（`repairTaskDates` 在不重疊時清成 null）、`tasks/[taskId]/route.ts:117-120`（改日期時清）
- **現象**：延期紅段的視覺依據是易被 repair/改日期清掉的暫存欄位，而非延期申請本身的權威紀錄。
- **後果**：已核准延期，甘特卻不顯示紅段。
- **建議**：延期段改由 `delayRequests` / baseline 這類權威資料推導。（不動 cascade，只改視覺資料來源。）

### #12 同日同任務同作者，內容被靜默覆蓋 🔀
