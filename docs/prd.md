# 專案看板系統 產品需求文件 (PRD)

## 1. 產品概述

### 產品願景與定位
- 打造一個直觀、協作式的專案管理平台，讓團隊能從專案啟動到結案，集中管理目標、流程與進度，並透過視覺化燈號與報表，即時掌握專案健康度與 KPI 達成狀況。
- 定位為企業團隊的內部專案管理與協作工具，聚焦於流程透明化與目標追蹤。

### 商業目標
- 提升跨部門專案協作效率，減少溝通與進度追蹤的行政成本。
- 確保專案執行與初始目標（效益、KPI）對齊，提高專案成功率。
- 透過數據化報表，為管理層提供決策支援。
- **節省管理時間和增強團隊協作透明度，讓主管能更直觀地了解專案現況並即時協助解決問題。**

### MVP 範圍定義
- 核心功能為：建立專案（含 SMART 目標、預期效益、專案說明）、時間軸任務管理與甘特圖、工作日誌追蹤、專案健康度燈號（紅黃綠）自動計算、延期申請與審核流程。
- 首版將不包含複雜的分析報表與進階後台管理功能，僅提供最基礎的專案數據概覽與 PDF 報告匯出。
- 首版使用 Mock 驗證機制（硬編碼使用者 + 統一密碼），不含真實身分驗證與 SSO 整合。

## 2. 使用者分析

### 目標使用者 Persona
- **專案經理 (PM)**：負責建立專案、設定 SMART 目標與 KPI、規劃里程碑與任務、分配任務、監控整體進度與自動計算的健康度燈號。**可審核團隊成員提出的延期申請。**
- **團隊成員 (Member)**：執行被分配的任務，透過時間軸表格更新任務狀態，在任務下撰寫工作日誌記錄進度。**當任務需要延期時，可向 PM/主管提出延期申請。**
- **主管 (Executive)**：需要從儀表板總覽所有專案的燈號狀態與統計報表，審核延期申請，掌握高風險專案狀況。**在風險列表中僅顯示高影響度風險，以聚焦關鍵問題。**

### 使用者痛點與需求
- 痛點：專案啟動資訊（目標、流程）散落在不同檔案與郵件中，難以查找與對齊。
- 痛點：無法快速了解專案當前是否偏離目標或時程。
- **痛點：現有內建系統介面複雜、功能不足，且無法客製化以符合不同專案類型（如不同里程碑）的需求，導致團隊仍依賴 Excel 管理。**
- 需求：需要一個單一平台集中管理專案全生命週期資訊。
- 需求：希望有直觀的視覺化指標（如燈號）快速判斷專案狀態。
- 需求：需要能協作更新任務狀態與工作日誌，並保留歷程。
- **需求：希望系統能引導使用者以 SMART 原則填寫專案目標。**
- **需求：當專案進度延後時，團隊成員能向 PM/主管提出延期申請與協助請求。**

### 使用者旅程
1. **專案啟動階段**：PM 於系統中建立新專案，填寫基本資訊（專案名稱、專案代碼、專案類型、起訖時間、預算等），設定 SMART 目標與專案說明。**系統提供 AI 輔助功能（📋 規劃中），可根據輸入的專案基本資料自動解析並產出專案細節內容，或由使用者手動整理。** 建立過程支援草稿自動儲存，防止意外遺失。
2. **規劃與協作階段**：PM 在專案編輯彈窗中，透過「工作項目」分頁建立里程碑與任務，使用時間軸表格（TimelineTable）進行拖放排序與 inline 編輯。系統自動建立任務之間的順序相依關係。PM 可在「團隊成員」分頁管理專案團隊，在「風險管理」分頁新增與追蹤風險項目。
3. **執行與追蹤階段**：團隊成員在「我的任務」頁面查看被指派的所有任務，透過任務對話框撰寫工作日誌（TaskLog）記錄每日/每週進度。系統根據任務狀態自動計算專案健康度燈號（紅黃綠），並自動同步里程碑狀態與進度。專案詳情頁提供甘特圖視覺化時程與任務相依分析。**當任務需要延期時，成員可在「我的任務」頁面提出延期申請。**
4. **審核與報告階段**：PM 與主管在儀表板查看所有專案的 KPI 統計、風險列表、即將到期的里程碑、本週未更新的專案。主管審核延期申請（批准時系統自動級聯更新任務日期與基線）。系統可生成 PDF 報告匯出專案狀況。

## 3. User Stories

### 依角色分類的使用者故事

**身為專案經理 (PM)，我希望能...**
- US-PM-01: 建立一個新專案，並填寫專案名稱、專案代碼、專案類型、起訖時間、預算等基本資訊。
- US-PM-02: 在專案建立時設定符合 SMART 原則的目標，系統提供獨立欄位引導填寫（具體、可衡量、可達成、相關性、時限性）。
- US-PM-03: 在專案編輯介面中，透過時間軸表格建立里程碑與任務，支援拖放排序與 inline 編輯，並可批次儲存變更。
- US-PM-04: 將任務指派給特定成員，並設定開始日期與截止日期。
- US-PM-05: 在專案詳情頁查看甘特圖，視覺化任務時程、相依關係與關鍵路徑，並支援多種時間尺度（日/週/月/季/年）。
- US-PM-06: 系統根據任務完成狀態自動計算專案健康度燈號（紅、黃、綠），無需手動設定。
- US-PM-07: 審核團隊成員提出的延期申請，選擇批准或駁回並填寫意見，批准時系統自動更新相關日期。
- US-PM-08: 管理專案風險項目（新增、編輯、關閉），包含影響度、機率、緩解措施等資訊。
- US-PM-09: 儲存里程碑基線快照，用於比較原始計畫與實際進度的差異。
- US-PM-10: 在建立專案的過程中隨時儲存草稿，下次可繼續編輯。
- US-PM-11: ✅ 在專案中上傳或連結關鍵文件，如專案目標、效益評估、流程圖。（📋 規劃中 — 目前系統尚未實作檔案上傳功能）

**身為團隊成員 (Member)，我希望能...**
- US-Member-01: 在登入後，於「我的任務」頁面一目了然地看到我被指派的所有任務，按專案分組顯示。
- US-Member-02: 透過任務對話框更新任務狀態，並在任務下撰寫工作日誌（TaskLog）記錄進度、工時與日期。
- US-Member-03: 在系統中查看專案的 SMART 目標、專案說明及健康度燈號，了解專案全貌。
- US-Member-04: 當任務需要延期時，在「我的任務」頁面提出延期申請，填寫延期原因、新的預估截止日期與受影響的里程碑。
- US-Member-05: 在個人資料頁查看我的任務統計（總數、已完成、進行中、待開始）、參與專案列表與近期活動紀錄。
- US-Member-06: 在任務卡片上添加評論與附上檔案。（📋 規劃中 — 目前以工作日誌替代評論功能，檔案上傳尚未實作）

**身為主管 (Executive)，我希望能...**
- US-Leader-01: 在儀表板總覽所有進行中專案的名稱、負責 PM 及當前健康度燈號（系統自動計算）。
- US-Leader-02: 查看 KPI 統計：專案總數、各燈號數量、平均進度、預算使用率。
- US-Leader-03: 查看高風險專案列表（僅顯示高影響度風險），即時掌握需要關注的問題。
- US-Leader-04: 審核延期申請，選擇批准或駁回並填寫意見，批准時系統自動級聯更新日期與基線。
- US-Leader-05: 查看即將到期的里程碑（30 天內）與本週未更新活動的專案列表。
- US-Leader-06: 取得 PDF 格式的專案報告，包含統計、狀態分佈與專案詳細資訊。

### 驗收標準（Acceptance Criteria）
- **US-PM-03 的 AC**：
  - 在專案編輯彈窗的「工作項目」分頁中，PM 可透過時間軸表格新增里程碑與任務。
  - 支援拖放排序（@dnd-kit/sortable），拖放後排序立即更新。
  - 支援 inline 編輯任務欄位（標題、指派人、日期、狀態、進度等）。
  - 變更以批次方式儲存（computeWorkItemsDiff 計算差異 → 6 步驟批次 API 呼叫）。
- **US-PM-06 的 AC**：
  - 系統根據以下規則自動計算專案健康度：
    - 🟢 綠燈：所有任務已完成，或無逾期/受阻任務。
    - 🟡 黃燈：有任何逾期或受阻任務（但未達紅燈門檻）。
    - 🔴 紅燈：逾期任務超過 30%、受阻任務超過 20%、或專案已過截止日但仍有未完成任務。
  - 燈號在儀表板、專案列表、專案詳情頁等處清晰顯示。
- **US-Member-04 的 AC**：
  - 在「我的任務」頁面中，成員可找到「申請延期」按鈕。
  - 申請表單需包含：延期原因、新的預估截止日期、受影響的里程碑清單。
  - 提交申請後，PM 與主管可在「延遲審核」頁面查看待處理的申請。
  - （📋 規劃中）提交申請後，相關審核者應收到站內通知。
- **US-Leader-01 的 AC**：
  - 主管登入後，可從側邊欄進入儀表板頁面。
  - 儀表板上以卡片形式展示每個專案的名稱、負責人（PM）和燈號圖示（紅、黃、綠）。
  - 顯示 KPI 統計卡片：專案總數、各燈號數量、平均進度、預算使用率。
  - 額外顯示：高風險列表、即將到期里程碑、本週未更新專案、待審核延期申請數量。

## 4. 功能需求（MoSCoW 優先級）

### Must Have：MVP 核心功能

- **專案管理核心** ✅：
  - 建立/編輯/刪除專案（基本資訊：名稱、專案代碼、專案類型、描述、起訖時間、預算、負責人）。
  - **專案建立時，需填寫專案層別、需求來源、專案類型、開案原因、預期效益、專案需求描述等欄位。**
  - **SMART 目標設定：提供獨立欄位引導使用者填寫符合 SMART 原則的目標（具體、可衡量、可達成、相關性、時限性）。**
  - **AI 輔助專案建立（📋 規劃中）：** 根據使用者輸入的專案基本資料，自動解析並產出建議的專案細節內容（如任務、里程碑大綱），使用者可選擇採用或手動編輯。目前 UI 已有入口，點擊後顯示「功能開發中」提示。
  - **專案草稿功能：** 建立專案過程中可隨時儲存為草稿，支援列表管理（查看/編輯/刪除草稿）。
  - 專案文件管理：上傳、下載、刪除、版本歷程查看。（📋 規劃中 — 目前系統尚未實作檔案上傳功能）

- **時間軸任務管理** ✅：
  - 使用時間軸表格（TimelineTable）作為主要任務管理介面，支援類似試算表的操作體驗。
  - 里程碑與任務的 inline 新增、編輯、刪除，支援拖放排序（@dnd-kit/sortable）。
  - 批次儲存變更：computeWorkItemsDiff 計算差異，透過 6 步驟 API 呼叫（delete tasks → delete milestones → create milestones → update milestones → create tasks → update tasks）。
  - 任務欄位：標題、指派人、開始/結束日期、狀態（todo/in_progress/done/blocked）、進度百分比、描述。
  - 系統在建立專案時自動建立任務之間的順序相依關係，並提供重建相依性的 API。
  - 看板視圖（KanbanBoard）作為輔助介面，提供 4 欄拖放看板。（🔧 部分實作 — UI 元件存在但尚未連接 API）

- **甘特圖與相依分析** ✅：
  - 專案詳情頁提供完整的甘特圖功能（自建 GanttChart 元件 + GanttDependencyOverlay），視覺化任務時程與里程碑。
  - 支援拖拉調整任務時間、任務相依關係箭頭顯示。
  - 支援多種檢視模式：日/週/月/季/年。
  - 任務相依分析 Tab：關鍵路徑計算、影響分析。

- **工作日誌（TaskLog）系統** ✅：
  - 團隊成員在任務下撰寫工作日誌，記錄工作內容、日期與工時。
  - 完整 CRUD：新增、編輯、刪除日誌，支援篩選和分頁。
  - 工作日誌支援草稿自動儲存至 localStorage，防止意外遺失。
  - 「更新紀錄」Tab 自動彙整所有任務日誌，按成員/日期分組顯示。
  - 儀表板根據 TaskLog 活動追蹤「本週是否有更新」。

- **專案健康度燈號** ✅：
  - 系統根據任務完成狀態**自動計算**專案健康度燈號，PM 無法手動覆蓋：
    - 🟢 綠燈：所有任務已完成，或無逾期/受阻任務。
    - 🟡 黃燈：有任何逾期或受阻任務。
    - 🔴 紅燈：逾期 >30%、受阻 >20%、或專案已過截止日。
  - 燈號在儀表板、專案列表、專案詳情頁等處清晰顯示。

- **里程碑基線功能** ✅：
  - 支援儲存里程碑基線快照，用於比較原始計畫與實際進度的差異。
  - 完整 CRUD API：建立基線、查看基線歷史。
  - 延期申請核准時自動重設基線。

- **自動同步機制** ✅：
  - `syncMilestoneStatus`：根據任務完成比例自動更新里程碑狀態。
  - `syncTaskProgressFromLogs`：根據工作日誌自動更新任務進度。
  - `autoProgressTasks`：自動將已過開始日期的 todo 任務推進為 in_progress。

- **延期申請流程** ✅：
  - **由團隊成員（Member）在「我的任務」頁面發起**，填寫延期原因、新日期及受影響的里程碑。
  - PM 與主管（Executive）可在「延遲審核」頁面查看待處理申請，選擇批准或駁回並填寫意見。
  - **批准時系統自動級聯更新**：更新對應任務的結束日期 + 重設里程碑基線。

- **基礎權限與角色** ✅：
  - 系統目前有三個角色：**PM（專案經理）**、**Member（團隊成員）**、**Executive（主管）**。
  - 權限邏輯：
    - Member 只能看到自己參與的專案。
    - PM 和 Executive 可以看到所有專案。
    - Executive 在風險列表中僅顯示高影響度（high）風險。
    - PM 和 Executive 可審核延期申請。
  - 目前使用 Mock 驗證機制（硬編碼使用者清單 + 統一密碼 "demo"），登入後存入 localStorage。（📋 未來應升級為真實身分驗證）

- **儀表板** ✅：
  - KPI 統計卡片：專案總數、各燈號數量分佈、平均進度、預算使用率。
  - 風險列表：紅/黃燈專案的風險項目（Executive 僅顯示高影響度）。
  - 即將到期里程碑：30 天內到期且未完成的里程碑。
  - 本週未更新專案：根據 TaskLog 活動判斷本週是否有更新。
  - 待審核延期申請數量。

- **報告功能** ✅：
  - 報告頁面：統計、狀態分佈、專案詳細資訊、團隊工作量分佈。
  - PDF 報告匯出：使用 jsPDF 在前端生成 PDF，包含專案資訊、任務狀態統計與工作日誌。
  - AI 報告產生（📋 規劃中）：可選擇週報/月報、PPT/Word/PDF 格式，自動從 DB 資料產生報告。目前 UI 已有入口，點擊後顯示「功能開發中」提示。

- **通知系統**（🔧 部分實作）：
  - UI 已有通知鈴鐺圖示與設定頁面。
  - 通知偏好目前存在 localStorage。
  - （📋 規劃中）後端通知 API 與觸發邏輯尚未實作。
  - （📋 規劃中）當延期申請提交時、任務被指派時、專案文件更新時，相關使用者應收到通知。

- **個人資料頁** ✅：
  - 使用者可檢視和編輯個人資訊（姓名、Email、組織/部門）。
  - 顯示統計資訊：參與專案數、任務狀態分佈（總數、已完成、進行中、待開始）。
  - 顯示參與專案列表（可點擊跳轉）與近期活動紀錄。

- **預算追蹤** ✅：
  - 每個專案有 budget（預算）和 budgetUsed（已使用預算）欄位。
  - 儀表板計算整體預算使用率（budgetUtilization）。

### Should Have：重要但可稍後

- **燈號自動化規則進階配置**：
  - 允許 PM 為專案自訂燈號計算的門檻值（例如調整逾期百分比門檻）。目前門檻為固定值。
- **簡易分析報表進階功能**：
  - 專案內報表：任務完成趨勢圖、成員工作量分佈趨勢。
  - 後台報表：專案健康度分佈圓餅圖、歷史趨勢分析。
- **專案文件管理**：
  - 支援上傳常見檔案格式（PDF, DOCX, PNG, JPG）至專案。
  - 文件線上預覽（如 PDF、圖片）。
  - 文件審核流程：提交審核 → 主管批註/通過。
- **專案範本**：
  - 可將現有專案結構（里程碑、任務清單）存為範本，供建立新專案時使用。
  - **支援依據不同「專案類型」套用不同的里程碑範本，以滿足客製化需求。**
- **真實身分驗證**：
  - 以 JWT 或 Session 機制替換現有 Mock 驗證。
  - 使用者密碼需以雜湊（Hash）方式儲存。
  - 支援與公司現有帳號系統（如 LDAP/AD）進行 SSO 整合。
- **成員在線狀態顯示**：
  - 在專案頁面或團隊成員列表中，顯示使用者頭像及在線（綠色圓點）/離線（灰色圓點）狀態指示。

### Could Have：錦上添花

- **個人化儀表板**：
  - 使用者可自訂首頁，放置常用專案、個人任務清單等小工具。
- **行事曆視圖**：
  - 將所有任務的截止日期以月曆形式呈現。
- **第三方整合**：
  - 支援以 Webhook 方式發送通知至 Slack/Microsoft Teams。
- **AI 進階功能**：
  - AI 自動根據工作日誌（TaskLog）內容，生成週報/月報摘要。
  - AI 輔助風險識別：根據專案狀態自動建議風險項目。
- **任務評論系統**：
  - 在任務下方提供獨立的評論區，與工作日誌分開。支援 @mention 成員與附件上傳。
- **即時協作指示**：
  - 在任務管理介面即時顯示其他成員正在編輯哪個任務。

### Won't Have：明確排除（MVP 範圍外）
- 完整的專案財務預算追蹤模組（目前僅有基礎的 budget/budgetUsed 欄位）。
- 與版本控制系統（如 Git）的深度整合。
- 手機原生應用程式（MVP 優先以 Web 響應式設計為主）。
- 複雜的多層級簽核流程（目前延期審核為單層 PM/Executive 審核）。

## 5. 非功能性需求

### 效能
- 頁面主要功能載入時間（在標準網路環境下）應小於 3 秒。
- 時間軸表格拖放排序與甘特圖操作的反饋延遲應小於 100 毫秒。
- 系統應能支援至少 50 個專案與 5000 個任務同時運作。

### 安全性
- 所有傳輸資料必須使用 HTTPS 加密。
- （📋 規劃中）使用者密碼需以雜湊（Hash）方式儲存。目前為 Mock 驗證，統一密碼 "demo"。
- （📋 規劃中）嚴格實作角色權限控制（RBAC），確保使用者只能存取被授權的專案與功能。目前已有基礎角色權限（PM/Member/Executive 可見性差異），但 API 層面的權限檢查尚不完整。
- （📋 規劃中）檔案上傳需進行副檔名過濾。目前系統尚未實作檔案上傳。

### 可用性
- 介面設計需符合直覺操作，參考主流專案管理工具的使用模式，**並避免過於複雜，以解決現有系統「不好用」的問題。**
- 系統需為響應式網頁設計（RWD），能適應桌面、平板等不同螢幕尺寸。
- 提供明確的操作指引與工具提示（Tooltip），特別是首次使用時間軸表格、甘特圖與燈號功能時。

### 可靠性
- 系統核心服務（專案存取、任務更新）的可用性目標為 99.5%。
- 需建立定期自動備份機制，確保資料可恢復。
- 關鍵操作（如刪除專案、刪除任務）需有二次確認彈窗。
- 專案草稿與工作日誌草稿需有自動儲存機制，防止資料遺失。

## 6. 成功指標（KPI）

### 量化的成功標準
- **使用者採用率**：上線三個月內，目標團隊的註冊使用者啟用率達 80%（啟用定義為至少建立一個任務或更新一次狀態）。
- **專案覆蓋率**：六個月內，公司內 70% 的新啟動專案使用此系統進行管理。
- **操作效率**：相較於舊方法（如 Email+Excel），專案狀態同步的頻率提升 50%（透過系統日誌衡量）。
- **使用者滿意度**：透過季度問卷，獲得淨推薦值（NPS）不低於 +30。
- **管理效率**：專案延期申請從提出到主管回覆的平均時間縮短 30%。

### 衡量方式
- 採用率與覆蓋率：透過後台數據分析使用者活躍度與專案創建數量。
- 操作效率：比對系統內任務狀態更新次數與過往同期間團隊的郵件往來次數（需定義對照基準）。
- 使用者滿意度：定期發放線上問卷進行調查。
- 管理效率：分析系統內延期申請流程的日誌記錄。

## 7. 風險與假設

### 已知風險與應對方案
- **風險**：團隊抗拒改變，不願從現有工具（如 Excel, Email）遷移。
  - **應對**：由上而下推動，先從一個示範團隊開始，展示效益。提供簡易的資料導入範本。
- **風險**：自動計算的燈號門檻值不適用於所有專案類型，導致燈號參考價值降低。
  - **應對**：在 Should Have 階段提供門檻值自訂功能，讓 PM 根據專案特性調整。同時持續觀察門檻值的合理性並調整預設值。
- **風險**：系統初期效能不佳，時間軸表格與甘特圖操作卡頓影響使用者體驗。
  - **應對**：在開發階段進行效能優化，善用虛擬滾動與懶載入技術，並設定明確的效能驗收標準。
- **風險**：AI 輔助產出的專案細節不符合實際需求，增加使用者調整負擔。
  - **應對**：將 AI 功能定位為「輔助」與「建議」，產出內容必須讓使用者能輕鬆編輯與調整，並收集使用回饋持續優化模型。
- **風險**：Mock 驗證機制不適合正式部署，存在安全風險。
  - **應對**：在正式上線前，必須將 Mock 驗證替換為真實身分驗證（JWT/Session + 密碼雜湊）。

### 關鍵假設
- 假設目標使用者已具備基本的專案管理概念（如任務、截止日期、里程碑）。
- 假設公司內部網路環境穩定，足以支援 Web 應用程式的正常操作。
- 假設管理層願意支持並要求團隊使用此系統進行專案追蹤。
- **假設團隊能接受並遵守在任務下定期撰寫工作日誌的要求。**
